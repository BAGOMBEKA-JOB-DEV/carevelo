# Endpoint Catalogue

> **Status:** Draft
> **Last reviewed:** 2026-08-13
> **Derives from:** [Domain Model](../20-domain/domain-model.md), [API Conventions](api-conventions.md)

MVP endpoints, grouped by bounded context. Conventions in [API Conventions](api-conventions.md); permissions in [RBAC Matrix](../50-security-compliance/rbac-matrix.md).

No endpoint accepts a tenant identifier — tenancy comes from the host or the session ([Multi-Tenancy](../30-architecture/multi-tenancy.md)).

**Audience** column: P = patient, S = clinic staff (role-restricted), O = platform operator.

## Identity & sessions — [Auth](authentication-and-sessions.md)

| Method | Path | Audience | Notes |
|---|---|---|---|
| POST | `/v1/patients/{patient}/account` | S admin, front desk, clinician | Creates the patient's account and links `patients.user_id` for that record. Email address supplied by staff; **initial password generated by the server and returned once**. Leaves `phone` and `phone_verified_at` null. Audited as `patient.account_created` |
| POST | `/v1/auth/sign-in` | P, S | Email address **or** phone number, and a password. The only sign-in path. Response identical whether or not the identifier is registered |
| POST | `/v1/auth/sign-out` | P, S, O | Reachable while a password change is outstanding |
| GET | `/v1/me` | P, S, O | Current actor, role, abilities, and whether a password change is outstanding |
| POST | `/v1/me/password` | P, S | Requires `current_password`. Invalidates other sessions; discharges `password_change_required_at` |
| POST | `/v1/invitations/{token}/accept` | — | Single-use, tenant-bound, expiring. Token possession is the proof of the number |

While a patient's first password change is outstanding, `GET /v1/me`, `POST /v1/me/password` and `POST /v1/auth/sign-out` are the **only** rows in this catalogue a session may reach. Middleware refuses the rest ([Auth](authentication-and-sessions.md)).

## Delivery — [H4](../10-product/prd-h4-prescription-dispensing-delivery.md)

| Method | Path | Audience | Notes |
|---|---|---|---|
| GET | `/v1/deliveries` | S dispatcher | The dispatch board |
| POST | `/v1/deliveries` | S dispatcher | **Rejected if the order contains a controlled item** |
| POST | `/v1/deliveries/{id}/assign` | S dispatcher | |
| GET | `/v1/rider/deliveries` | S rider | **Only their own assignments** |
| GET | `/v1/rider/deliveries/{id}` | S rider | **Rider serialisation: recipient, address, contact, package reference. No clinical fields** |
| POST | `/v1/rider/deliveries/{id}/status` | S rider | One transition endpoint, not four verbs. Reason from a fixed list on failure |
| GET | `/v1/deliveries/{id}` | S dispatcher, S rider assigned | Full record. Distinct from tracking below |
| GET | `/v1/deliveries/{id}/tracking` | P own, S | Status milestones. **Never contents** |

The rider endpoints are a separate namespace with distinct resource classes — not the dispatcher resource with fields hidden client-side ([API Conventions](api-conventions.md)).

**Deviation, accepted.** This document originally specified four rider verbs — `/picked-up`, `/en-route`, `/delivered`, `/failed`. One `POST .../status` is implemented instead, carrying the target status. The transitions are identical and the state machine refuses an illegal one, which is a better place for that rule than the routing table: with four verbs, "may this delivery go straight from assigned to delivered" is answered by which routes happen to exist, and the answer has to be repeated in each of them. Fewer routes, one place to change the lifecycle.

`GET /v1/deliveries/{id}` and `GET /v1/deliveries/{id}/tracking` are deliberately separate abilities rather than one endpoint serialised two ways. The first returns the record — recipient, address, and an order whose items are medicines. The second returns statuses and timestamps. The patient waiting for the delivery holds the second and not the first, and a shared endpoint would put that distinction in a resource class where a careless change could undo it.

## Payments — [H5](../10-product/prd-h5-payments-non-custodial.md)

| Method | Path | Audience | Notes |
|---|---|---|---|
| POST | `/v1/payment-intents` | P, S front desk | **`Idempotency-Key` required.** Uses the tenant's own credentials. Returns `redirect_url` where the aggregator is initiated server-side (Pesapal); `null` otherwise |
| GET | `/v1/payment-intents/{id}` | P own, S admin | Polled by the client while `pending` |
| POST | `/v1/payment-intents/{id}/attest-cash` | S front desk, S pharmacist | Audited attestation |
| GET | `/v1/payment-intents/{id}/receipt` | P own, S | Clinic named as payee |
| GET | `/v1/reconciliation` | S admin | Daily view; flags mismatches |
| GET | `/v1/reconciliation/export` | S admin | CSV for the clinic's own books |

`redirect_url` is **somewhere to send the patient, not a confirmation that anybody has paid.** The intent is still `initiated` when it is returned, and a client that treats its presence as a paid booking has confirmed a booking nobody paid for.

**Absent by design, permanently:** no balance, no wallet, no payout, no settlement, no platform-initiated refund. Those entities do not exist ([Payments Regulatory Boundary](../50-security-compliance/payments-regulatory-boundary.md)).

## Webhooks — inbound

| Method | Path | Notes |
|---|---|---|
| POST | `/webhooks/flutterwave/{tenant}` | Signature-verified against the tenant's secret |
| GET · POST | `/webhooks/pesapal/{tenant}` | **Not signed, and not signable.** Trusted for nothing |

All unauthenticated — an aggregator has no session with us — and all idempotent. **The two are not variants of each other**, and the second row used to say "Same", which was wrong in the way that matters.

Flutterwave signs its callback and carries the outcome in it: trust comes entirely from verifying that signature against the tenant's own webhook secret, on the raw body, constant-time.

Pesapal's notification carries `OrderTrackingId`, `OrderMerchantReference` and `OrderNotificationType` — **no status, no amount, no signature**, and no shared secret from which one could be derived. Pesapal requires the merchant to call `GetTransactionStatus` itself. So the endpoint reads the tracking id and nothing else, resolves the attempt inside that tenant, and reads the outcome back from Pesapal over TLS with **the clinic's own credentials**. A forged notification can therefore only cause an authenticated re-read of a status Pesapal owns. `GET` as well as `POST`, because the notification type is registered per URL at Pesapal and both have been observed; neither is trusted more than the other.

An unknown tenant, an unconfigured clinic and an unknown tracking id all answer a neutral **404**, indistinguishable from one another.

Detail in [Webhooks](webhooks.md); the reasoning in [ADR-0012](../70-decisions/0012-pesapal-unsigned-ipn.md).

## Platform administration

| Method | Path | Audience | Notes |
|---|---|---|---|
| GET · POST | `/v1/platform/tenants` | O | Register, provision |
| PATCH | `/v1/platform/tenants/{id}` | O | Suspend, resume, offboard |
| POST | `/v1/platform/tenants/{id}/export` | O | Controller-obligation export ([Retention](../50-security-compliance/data-retention-and-deletion.md)) |
| POST | `/v1/platform/break-glass` | O | Reason and scope required; **notifies the tenant**; audited |
| GET | `/v1/platform/break-glass` | O, S admin | The grant register. A clinic administrator sees grants against their own clinic |
| GET | `/v1/platform/audit-events` | O | **Read-only.** Platform events in full; a clinic's events as **metadata only**. `?tenant_id=` chooses which trail is read |
| GET | `/v1/platform/health` | O | |

Platform endpoints reach **no clinical data** without an active break-glass grant.

`GET /v1/platform/audit-events` is the platform half of the evidence layer, and it exists because the other half is not reachable from a clinic: platform events — break-glass grants, tenant provisioning and suspension, TOTP enrolments, platform sign-ins — carry a null `tenant_id` and sit outside tenant row-level security, so nothing could read them back at all.

**One response is one trail.** Without `tenant_id` it reads the platform's own events; with one it reads that clinic's, and a clinic's events come back as the ENVELOPE and never the payload — no `metadata`, no `subject_id`, no `ip_address`, no `user_agent`. `projection` on each row says which of the two it is. Record-level detail is what a break-glass grant is for, and that is reason-recorded, time-boxed, tenant-notified and audited ([Audit Logging](../50-security-compliance/audit-logging.md), [RBAC Matrix](../50-security-compliance/rbac-matrix.md)).

Reading it is itself audited, into the platform trail, naming the clinic whose trail was read.
